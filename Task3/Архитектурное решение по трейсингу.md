## Cистемы которые нужно покрыть трейсингом
1. Shop API 
- входящие HTTP-запросы
- операции с БД
- таймауты при загрузке/чтении 3D files
2. RabbitMQ
- publish, enqueue, deliver, ack
- задержка доставки
- маршрутизация
3. MES API
- consume/publish события RabbitMQ
- бизнес-операции
- операции с БД
- таймауты при загрузке/чтении 3D files
4. CRM API
- consume/publish события RabbitMQ
- бизнес-операции
- операции с БД
- таймауты при загрузке/чтении 3D files

## Какие данные должны попадать в трейсинг
- Корреляционные идентификаторы:
  - trace_id, span_id
  - order_id (ключ для сквозного поиска)
  - message_id (для RabbitMQ)
- Бизнес-контекст:
  - order_status_from, order_status_to
  - operation_name
  - user_id_hash
- Производительность:
  - service_name (shop|mes|crm)
  - start_time, duration_ms
  - retry_count
  - timeout_flag
- Ошибки:
  - error_type
  - error_message
  - dlq_flag
- Технический контекст:
  - env (dev|release|prod)
  - instance_id (если внедряется)
  - version
  - http.method, http.route, http.status (для API)
  - queue_name, exchange (для RabbitMQ)
  - db.system

## Мотивация
Трейсинг нужен, потому что заказ проходит через несколько систем и асинхронные очереди, а без сквозной видимости 
невозможно быстро понять, где он завис или сломался. Компании это даст сокращение времени разбора инцидентов, 
более стабильные релизы, контроль SLA по жизненному циклу заказа.

### Метрики, на которые повлияет внедрение трейсинга:
- Доля заказов, застрявших в статусах: снизится за счёт раннего обнаружения зависаний в RabbitMQ или интеграциях.
- Error rate (5xx / failed transitions): уменьшится за счёт выявления источников ошибок в 
конкретных сервисах и зависимостях.
- Release failure rate / rollback rate: снизится потому что деградации после релизов будут видны сразу.
- p95/p99 latency ключевых операций заказа: уменьшится благодаря точечной оптимизации самых медленных шагов.
- MTTR (Mean Time To Recovery): снизится за счёт быстрого нахождения узкого места (сервис, очередь, БД, File Storage).

## Предлагаемое решение:
1. Внедрить OpenTelemetry SDK в Shop API, MES API, CRM API для автоматического трейсинга HTTP-запросов, 
операций с БД, файловым хранилищем и бизнес-операций.
2. Использовать Jaeger Collector для сбора и агрегации трейсинговых данных.
3. Использовать OpenSearch для хранения и анализа трейсинговых данных.
4. Использовать Jaeger UI для визуализации трейсинговых данных и быстрого поиска по trace_id, span_id, order_id, message_id.

## Компромиссы:
1. Высокая стоимость хранения и трафика при большом объёме:

При большом QPS и длинных трейcах стоимость хранения, сетевой трафик и нагрузка на сервисы 
могут стать заметными. Без семплинга, ретеншн-политик и фильтрации по бизнес-флоу трейсинг 
превращается в дорогой логгер всего.

2. Сложность внедрения и поддержки:

Внедрение OpenTelemetry требует изменений в коде, настройки агентов, интеграции с Jaeger и OpenSearch, 
а также обучения команды. Без централизованного управления и мониторинга трейсинг может стать источником 
технического долга и проблем с производительностью.

3. Организационная неготовность и отсутствие процессов реакции:

Если нет владельцев SLO, on-call, runbook’ов и практики разборов инцидентов, трейсинг не будет использоваться системно.
В итоге инструмент внедрён, но не влияет на MTTR/качество — деньги потрачены, эффекта для бизнеса нет.

4. Риск утечки данных и безопасности:

Трейсинг может содержать чувствительные данные (user_id_hash, order_id, message_id), 
и без правильной маскировки, шифрования и контроля доступа это может привести к утечкам данных и проблемам 
с безопасностью. Важно внедрить политики безопасности.

## Аспекты безопасности:
1. Маскировка данных: user_id_hash вместо user_id, order_id и message_id должны быть анонимизированы или 
хэшированы, чтобы предотвратить идентификацию конкретных пользователей или заказов.
2. Шифрование данных: трейсинговые данные должны быть зашифрованы как при передаче, так и при хранении, 
чтобы предотвратить несанкционированный доступ.
3. Контроль доступа: доступ к трейсинговым данным должен быть ограничен только авторизованными 
пользователями и сервисами, с использованием ролевой модели доступа.
4. Мониторинг и аудит: необходимо внедрить мониторинг доступа к трейсинговым данным и аудит действий,
чтобы быстро обнаруживать и реагировать на потенциальные нарушения безопасности.
5. Политика хранения данных: необходимо определить, как долго будут храниться трейсинговые данные  
и обеспечить их безопасное удаление после истечения срока хранения, чтобы минимизировать риски утечки данных.
