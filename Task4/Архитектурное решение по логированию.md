## Планирования логирования
### Системы из которых нужен централизованный сбор логов:
- Shop/MES/CRM APIs
- Shop/MES/CRM
- DBs
- RabbitMQ

### Какие логи собирать на уровне INFO:
Я описал самые приоритетные для бизнеса это Shop/MES/CRM APIs.

1.Shop API
- Создание заказа
    - user_id_hash 
    - total_price 
    - request_id
- Изменение статуса заказа
    - user_id_hash
    - status_from 
    - status_to 
    - request_id
- Работа с 3D файлами
    - file_id 
    - operation (upload|download|delete)
    - storage
2. MES API
- Начало бизнес-операции
    - operation_id
    - operation_type 
    - request_id
- Изменение производственного статуса
    - operation_id
    - status_from 
    - status_to 
    - request_id
- Публикация или получение события RabbitMQ
    - user_id_hash
    - event_type
    - message_id
- Запись в БД
    - operation_id
    - query_type (insert|update|delete)
    - request_id
- Работа с 3D файлами
    - file_id 
    - operation (upload|download|delete)
    - storage 
3. CRM API
- Обновление данных клиента по заказу
    - user_id_hash 
    - field_name 
    - old_value 
    - new_value 
    - request_id
- Публикация или получение события RabbitMQ
    - user_id_hash
    - event_type
    - message_id
- Запись в БД
    - operation_id
    - query_type (insert|update|delete)
    - request_id
- Работа с 3D файлами
    - file_id 
    - operation (upload|download|delete)
    - storage

**Общие обязательные поля для всех INFO-логов**

Добавлять в каждый лог:
- timestamp
- service_name (shop|mes|crm)
- env (dev|release|prod)
- order_id
- version
- instance_id (если применимо)

### Буду использовать другие уровни логирования:
- WARN: что-то пошло не так, но система выжила
    - повторная доставка сообщения из RabbitMQ 
    - таймаут при работе с файловым хранилищем, но повторная попытка успешна 
    - fallback-логика 
- ERROR: ошибки, влияющие на бизнес-флоу
    - сообщение ушло в DLQ
    - заказ не создан
    - транзакция БД не применена
    - 5xx при синхронных вызовах
    - невозможно обновить статус заказа
- DEBUG: для отладки, не должен попадать в прод
    - входные и выходные данные API
    - стек вызовов при ошибках
    - время выполнения ключевых операций

## Мотивация
Централизованное логирование даёт прозрачность того, что происходит с заказом на каждом шаге, позволяя быстро находить
причину сбоев и узкие места. Для компании это означает более быстрые разборы инцидентов, меньше простоя,
выше стабильность сервиса и лучшее качество клиентского опыта.

### Метрики (технические и бизнес), на которые повлияет внедрение
- Доля заказов без ретраев: вырастет за счёт обнаружения проблем с очередями и файловым хранилищем
- Процент застрявших или ошибочных заказов: снизится благодаря видимости точек отказа в цепочке
- Время реакции поддержки на инциденты клиентов: сократится за счёт сквозного поиска по order_id и request_id.
- MTTR (Mean Time To Recovery): снизится за счёт быстрых RCA по логам
- SLO/SLA по доступности API: улучшится из-за раннего выявления деградаций

### Приоритеты настройки логирование и трейсинга:
1. Shop API: входная точка всех заказов и основной источник клиентских ошибок.
2. MES API: важен для производственного процесса, сбои здесь влияют на выполнение заказов.
3. CRM API: влияет на качество обслуживания клиентов, ошибки здесь могут привести к недовольству клиентов.
4. RabbitMQ: критично для асинхронной коммуникации между сервисами, проблемы с очередями часто приводят к застреванию заказов.

Shop/MES/CRM APIs + RabbitMQ дадут максимальный эффект для поиска причин инцидентов и потерянных заказов.
С них стоит начать в первую очередь.

## Предлагаемое решение
Для централизованного логирования использовать ELK stack (Elasticsearch, Logstash, Kibana):
- Filebeat будет установлен на всех сервисах для отправки логов в Logstash
  - Log Shippers (Filebeat) на каждом инстансе сервиса, DB и RabbitMQ для отправки логов в Logstash
  - Добавляет метаданные: service, env, instance_id, version, order_id, timestamp
- Logstash будет собирать логи с сервисов парсить их и отправлять в Elasticsearch
- Elasticsearch будет хранить и индексировать логи, обеспечивая быстрый поиск по ним
  - Хранение логов в отдельных индексах по системе и окружению
  - ILM (Index Lifecycle Management): hot, warm, delete.
- Kibana будет использоваться для визуализации логов, создания дашбордов и настройки алертов
  - Дашборды по ошибкам, задержкам, статусам заказов
  - Настройка алертов на критические ошибки и аномалии в логах

### Политика безопасности логов:
Чувствительные данные:
- Запрещено логировать: персональные данные в явном виде (ФИО, e-mail, телефон), 
платежные реквизиты, токены, пароли, содержимое 3D-файлов.
- Разрешено: хэши/маски (например, user_id_hash, email_hash), технические идентификаторы (order_id, request_id).
Доступы (RBAC):
- Read-only: QA, поддержка
- Read/Write (доступ к saved dashboards): инженеры бэкенда/DevOps.
- Admin: DevOps управление индексами, ILM, алертами.
- Аудит: все доступы к Kibana логируются (audit logs).
Сегментация окружений:
- Раздельные пространства Kibana и индексы для dev, release, prod.
- Доступ в prod через VPN/SSO, MFA.

### Политика хранения (ретеншн, индексы, объёмы)
Индексация:
- Отдельные индексы по системе и окружению logs-shop-prod-*, logs-mes-prod-*, logs-crm-prod-*, logs-rabbitmq-prod-*
- Аналогично для dev и release
Шаблоны маппинга с обязательными полями:
- timestamp, service_name, env, order_id, request_id, version, instance_id
Ретеншн:
- dev: 7–14 дней (быстрые итерации, низкая ценность долгого хранения).
- release: 30–60 дней (для анализа проблем в релизах, которые могут проявиться позже).
- prod: 90–180 дней (для долгосрочного анализа инцидентов, трендов, RCA).
Объёмы и контроль:
- Лимиты на размер индексов (например, 50–100 ГБ/индекс) с rollover по времени/размеру.
- Семплинг INFO-логов для высокочастотных эндпоинтов (оставлять бизнес-события и ошибки всегда).
- Алерты на рост объёма логов и ошибки парсинга.

## Мероприятия для превращения системы сбора логов в систему анализа логов
1. Настройка дашбордов в Kibana для мониторинга ключевых метрик (ошибки, задержки, статусы заказов).
2. Настройка алертов на критические ошибки и аномалии в логах (например, рост количества 5xx ошибок, застревание заказов).
3. Регулярные RCA (Root Cause Analysis) инцидентов с использованием логов для выявления причин и узких мест.
4. Обучение команды работе с Kibana, поиску по логам и интерпретации данных для быстрого реагирования на инциденты.
5. Постоянное улучшение логирования на основе анализа инцидентов и обратной связи от команды 
(добавление новых полей, изменение уровней логирования, оптимизация формата логов).
6. Периодический аудит логов на предмет чувствительных данных и соответствия политики безопасности.
7. Внедрение практики "log-driven development" для улучшения качества логов и их полезности для анализа.
