## Потенциальные проблемные места
1. **Слабая observability**
- Нет централизованного мониторинга бизнесовых и инфраструктурных метрик (metrics)
- Отсутствие централизованного логирования (logs)
- Отсутствие централизованного сбора трейсов внутренних вызовов (traces)
2. **Single point of failure во всех критичных компонентах**
- Один инстанс каждого сервиса и каждой БД
- RabbitMQ как единая точка отказа: нет кластеризации, нет репликации, нет резервного брокера
- Отсутствие масштабируемости под нагрузкой: нет автоскейлинга, нет балансировки
- Не упомянуто резервное копирование данных и планы восстановления
3. **Cлабые QA процессы**
- Отсутствие автоматизации в тестовом контуре: QA-инженер прогоняет E2E-сценарии вручную 
поэтому рост задержек релизов, низкая масштабируемость процесса тестирования
- Нет упоминания о smoke, интеграционном и нагрузочном тестировании 
- Явная нехватка специалистов по тестированию: один QA-инженер на весь проект со слабым опытом автоматизации
4. **Слабые CI/CD: ручной деплой в release и prod**
- Риск человеческой ошибки при деплое
- Длительное время релиза из-за ручных шагов
- Нет упоминания быстрого rollback
5. **Сильная связность сервисов на уровне бизнес-логики**
- Доменная логика размазана по системам
6. **Риски рассинхронизации статусов заказа между системами**
- Статусы меняются в разных системах (Shop, MES, CRM) без явного процесс-менеджмента
- Не упоминаются подходы к гарантии доставки и идемпотентности событий: возможны дубли, пропуски событий, 
двойные переходы статусов.

## Инициативы необходимые для устранения нежелательных ситуаций
1. **Внедрение централизованной observability платформы**
- Внедрить систему мониторинга (например, Prometheus + Grafana) для сбора метрик бизнес-логики и инфраструктуры
- Внедрить централизованное логирование (например, ELK stack) для сбора и анализа логов
- Внедрить систему трассировки (например, Jaeger) для отслеживания внутренних вызовов и выявления узких мест
2. **Реализация отказоустойчивой архитектуры**
- Внедрить кластеризацию RabbitMQ и репликацию БД для устранения single point of failure
- Внедрить балансировщики нагрузки и автоскейлинг для обеспечения масштабируемости под нагрузкой
- Разработать и внедрить планы резервного копирования данных и восстановления после сбоев
3. **Усиление QA процессов**
- Автоматизировать тестирование: внедрить CI/CD пайплайны для автоматического запуска smoke, интеграционных и нагрузочных тестов
- Нанять дополнительных QA-инженеров с опытом автоматизации тестирования для увеличения пропускной способности тестового процесса
- Внедрить практики тестирования на ранних этапах разработки (shift-left testing) для выявления дефектов на ранних стадиях
4. **Автоматизация CI/CD процессов**
- Внедрить автоматические пайплайны для деплоя в release и prod, чтобы минимизировать человеческий фактор и ускорить релизы
- Внедрить механизмы быстрого rollback для обеспечения возможности быстрого отката в случае проблем после релиза
5. **Рефакторинг архитектуры для снижения связности**
- Внедрить четкую границу между сервисами и доменами, чтобы бизнес-логика была сосредоточена в соответствующих сервисах
- Внедрить API Gateway для управления взаимодействием между сервисами и обеспечения четкой контрактной границы
6. **Управление статусами заказов и гарантии доставки**
- Внедрить централизованную систему управления статусами заказов, которая будет синхронизировать статусы между Shop, MES и CRM
- Внедрить механизмы гарантии доставки и идемпотентности событий, чтобы избежать дублирования, пропусков и двойных переходов статусов. 
Например, использовать уникальные идентификаторы событий и механизмы повторной отправки при неудаче.
